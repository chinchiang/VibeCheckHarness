## 2. 使用者決定的設計變更（`rule_version 05-v0.16`）

三項都在裁決與測試證據分類。沒有任何範例的裁決狀態因此改變：範例中沒有 `REJECTED` 的裁決，也沒有分析者不同意的結果；兩個沒有正對照的 PASS 改了類別名稱。

### D2 高嚴重度的叢集不自動駁回

- **問題**（代理回報，規則原文讀碼確認）：兩條規則把叢集直接判為 `REJECTED`，不成為種子威脅、不進人工關卡——R0（成員的證據沒有任何一項接地）與 R4 第 8 列（單一家族回報、反駁分數過 θ_reject）。受測 repo 是攻擊者可控的輸入，所有驗證者讀同一份程式碼，一段偽裝的 guard 或註解可以同時誘導它們反駁；LLM 也常改寫片段而不是逐字引用，真缺陷會落到 R0。Lite 不做抽查。
- **選項**：A 維持現狀；B rubric 嚴重度為 critical／high 的叢集改為 `DISPUTED` 送 G2；C 全面取消自動駁回，另立「低優先、未驗證」註記。
- **決定**：B。嚴重度由程式依 inventory 計算（`derive.rubric_severity`），不是模型自報，拿它當分流條件不會被注入繞過；改動範圍可控。
- **處理**：`adjudicate.Inputs.high_severity`。R0 → `DISPUTED`（決策表第 17 列）；R4 第 8 列落到第 9 列 `DISPUTED`；Lane A（R9）給 `UNCORROBORATED` 而不是 `REJECTED`。G2 的駁回（R10）是人的決定，不受影響。
- **未做**：校準語料的對抗子集（植入缺陷加上誘導反駁的註解）屬於校準實驗設計，尚未處理。

### D4 結果分析者的不同意不否決事先登記的證明

- **問題**（讀碼）：合格的 Result Analyst 不同意時，結果一律降為 `E_inc`，即使解讀已事先登記。分析者讀的是受測應用的回應或測試輸出，可被誘導輸出「不同意」，把 G4 核准、重播成立的確定性 FAIL 降級。
- **第十輪的決定**：[第十輪紀錄](review-2026-10-27-r10.md)把它改成「一律 `E_inc`」，理由是當時程式與 05 §4.2 的文字不一致，沒有其他設計理由。
- **選項**：A 維持現狀；B 事先登記的結果分類不變、裁決加註並列入人工複核；C 事先登記的結果完全不呼叫分析者。
- **決定**：B。保留訊號、移除否決權。未事先登記的結果仍是 `E_inc`。
- **處理**：`derive.classify_result` 在事先登記時保留類別，理由帶 `analyst_disagrees`；裁決加註 `analyst_disagrees`（R12）。

### D6 沒有正對照的合格 PASS 另立類別

- **問題**（讀碼）：測試案例只強制 `reachability` 對照。沒有 `oracle_can_fail` 對照的 PASS 與有正對照的同屬 `E_pass`，範例還附「上界 4.9%」。LLM 類測試的 oracle 常讀受測應用自己寫的紀錄，有漏洞的路徑沒寫紀錄時也會 PASS；此時上界量到的是「紀錄有沒有寫」。
- **已有的處理**：R11 原本就區分兩者（沒有正對照只加註、不把確認改成 `DISPUTED`）。問題在類別名稱相同，以及報告仍陳述統計上界。
- **選項**：A 維持現狀；B 另立類別、不陳述上界；C 高風險或 oracle 資料來自受測應用時強制正對照。
- **決定**：B。修的是「報告誤導」，不強迫每個測試準備植入版。
- **處理**：新類別 `E_pass_weak`；`Inputs.pass_positive` 移除，改由類別表達；`test_not_reproduced` 的理由在沒有 `E_pass` 時不得陳述統計上界（`E-VERDICT-ANNOTATIONS`，樣式檢查）。範例 `verdict.k-011-b5` 的理由拿掉 `p_u≈0.049`。
- **限制**：樣式檢查擋不住換句話說，列為 06 §3 #47。

- **D5（無法證明唯讀的 GET／HEAD 視為寫入）已實作**：`safety.is_mutation` 只把「W0 inventory 的 `writes` 為 false」或「seed manifest 的 `read_only_endpoints` 宣告」的 GET／HEAD 當讀取，其餘是寫入（要綁種子、至少 S1；綁不了就是 S3）。`read_only_endpoints` 的 schema 開放 GET／HEAD。範例種子清單補上兩個 inventory 不認得的 GET；範例測試案例的安全等級都沒變。沒有處理的部分列為 06 §3 #48：LLM／agent 測試在伺服器端的副作用，請求層仍然看不到；GraphQL query 的綁定仍待 BL-35。
- **D3（W4 之後由人逐項核准 LLM 撰寫的 oracle）已實作，`rule_version 05-v0.17`**：
  - 問題（讀碼）：`05-v0.15`／`05-v0.16` 以叢集的 G2 `accept` 作為 LLM 撰寫 W4 測試的事先登記入口。G2 在 W4 之前，人接受叢集時測試還不存在，沒有人讀過後來把該叢集判為 `CONFIRMED_EXECUTABLE` 的 oracle。
  - 選項：A 維持；B 移除 G2 入口，W4 之後逐項核准 oracle 並綁定雜湊；C 移除入口、不加步驟（這類測試最高 `LIKELY`）。決定：B。
  - 處理：G3 紀錄新增選用欄位 `oracle_approvals[]`（`testcase_id`、`testcase_sha256`、`accept`／`reject`），隨紀錄簽章；`derive.w4_oracle_approved` 取該 run 最新一筆非 EXPIRED 的 G3 紀錄中提到該測試的項目，要求 `accept` 且雜湊等於測試案例現在的 approval hash；只對 G3 之後的裁決版本生效；`derive.g2_accepted` 移除，G2 的決定不再影響任何測試證據的分類。validator 新增 `E-GATE-ORACLE`。
  - 放在 G3 而不是新關卡的理由（實作時我的判斷）：G3 是 W4 之後第一個由人簽章的關卡，審查者相同；不新增關卡就不必改關卡順序、逾時與角色的規則。核准另列一個清單、不混進 `decisions`，因為既有規則假設 G3 的決定項目都是威脅。
  - 影響：範例的裁決狀態都沒變（範例的 W4 測試是程式產生 oracle 的 `local_rls`，不需要核准）。沒有 G3 的 run（只做白箱）裡，LLM 撰寫的 W4 FAIL 維持最高 `LIKELY`——這等於選項 C 的結果，是 B 在沒有人工關卡時的必然下限。
  - 未做：Gate Service 呈現這個清單的介面與 `decisions.yaml` 的對應欄位屬於產品實作；範例中沒有 LLM 撰寫的 W4 測試，所以沒有一個帶 `oracle_approvals` 的簽章範例（測試以 fixture 改寫並重簽驗證）。
