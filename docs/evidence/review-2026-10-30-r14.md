# 設計審查紀錄：第十四輪（2026-10-30 r14，內部三組審查）

> **這份紀錄的用途**：保存對 `main@6b4dfb0`（第十三輪 PR1 合併後）的三組獨立審查核實結果、使用者的三項決定與處理方式，讓 run 紀錄規則的補強（PR1）、裁決與校準的修正（PR2，`rule_version 05-v0.14` → `05-v0.15`）與方法論、文件、流程的整理（PR3）都能追溯到審查發現。
>
> - **審查方式**：三個彼此獨立、只讀不寫的審查——A：validator 能否被繞過（記憶體 probe，重算雜湊、以 TEST ONLY 金鑰重簽）；B：裁決、投票、統計與校準（讀碼、重算數值）；C：方法論、文件一致性、路線圖可行性（逐行引文）。主審查者重跑最嚴重的項目（`probe_r14.py`）並讀碼確認原因，才列為成立。
> - **凍結規則**：依 [CONTRIBUTING](../../CONTRIBUTING.md#規格凍結第十二輪第二次外部審查起)，本輪修改屬於「審查核實成立的缺陷」；三處改變設計的地方（W4 事先登記、帶入叢集不投票、Lite 單機 profile 待訂）是使用者決定，記在 §2。
> - **機械性檢查在審查時全部通過**：1,835 個測試、主範例 4,807 項、四個變體、35 份突變清單 551 個突變全部 CAUGHT、連結與 generator 檢查。
> - **處理原則**：每個宣稱「修好」的錯誤都有回歸測試（修正前失敗、修正後通過）並以 `tools/mutation_check.py` 逐一停用確認。

## 1. 核實一覽

嚴重度：**高**＝能讓錯誤的狀態或報告通過驗證，或規格無法照寫實作；**中**＝規則有洞但需要配合條件，或只影響文件一致性；**低**＝文字與計數。「核實」欄：重跑＝主審查者在 `6b4dfb0` 上重現；讀碼＝主審查者讀碼確認。

## 2. 使用者的決定

1. **W4 事先登記**：只有由程式從 G1 核准結構產生的 oracle（`access_matrix` → `local_rls`、`llm_tools` → `fake_model`）算事先登記，且 `oracle_can_pass` 與 `oracle_can_fail` 都要 PASS；LLM 自由撰寫的 W4 測試 FAIL 上限 LIKELY（加註 `oracle_unreviewed`），經 G2 逐項確認後才升（`05-v0.15`）。
2. **帶入叢集不接受任何投票**：verdict 有票 → `E-VERDICT-VOTE`；狀態只由回歸測試證據決定。
3. **Lite 單機 profile 先不訂**：07 寫明「待訂」並列入待辦（BL-70）；MVP-0 實作計畫時再決定。

## 3. PR1：validator 繞過（A1–A10）

### 3.1 影響範圍

- **裁決語意**：沒有改變；`rule_version` 維持 `05-v0.14`。
- **範例語意**：主範例的 G0b（gate record、`run.gate_records`、事件）從 10-01 09:00 移到 20:00，B0 `ownership_check` 09:30 → 20:30，B1 事件 → 20:45，G3 開啟 10:00 → 21:00，`restore_drill` 10-02 09:00 → 20:30，全部落在 ROE 的週一～五 20:00–23:00 時窗；三個 run 的 `run_created` payload 新增 `baseline_run_id`（initial 為 null、跟進 run 指向 `run-2026-09-23-001`）。`regression` 變體的跟進 run 在 WAITING_GATE 之後補一筆時窗內的 `ownership_check`（10-07 20:30）。所有範例重簽、四個變體重建。
