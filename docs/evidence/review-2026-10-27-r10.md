# 設計審查紀錄：第十輪（2026-10-27 r10）

> **這份紀錄的用途**：保存第十輪審查的發現與處理方式，讓 `rule_version 05-v0.8` → `05-v0.9`、錨定模型的三個缺口與文件整併都能追溯到審查發現；也列出改變做法與留到之後的項目。
>
> - **審查對象**：main 的 `340b801`（第九輪 PR #24～#27 合併之後）。
> - **方式**：三個彼此獨立的唯讀審查，分別看 validator 與 schema 能否被繞過、裁決／統計／校準邏輯、方法論與文件。每項繞過都附在記憶體中重現的 probe；最嚴重的 5 項（重新打開已完成的 run、第二份報告 manifest、關卡紀錄改寫、θ_reject 單票駁回、自填 `sampled`）由主審查者重跑確認。
> - **機械性檢查在審查時全部通過**：validator 4,528 項、1,215 個測試、0 個壞連結、證據帳本與參考文獻最新、突變錨點 0 個過期、錯誤碼 304 個與程式雙向一致；決定表 13 列與程式在 143,360 組輸入上零不符，K-014 與 Clopper-Pearson 的數字可重現。
> - **處理原則**：依 [CONTRIBUTING.md](../../CONTRIBUTING.md)，每個宣稱「修好」的錯誤都有回歸測試：測試在修正前的 commit 上失敗、修正後通過，並且逐一停用每個新檢查確認對應的測試失敗（`tests/mutations/r10_*.json`，以 `tools/mutation_check.py` 重跑）。
> - **結果**：四個 PR 全部合併；改變做法見 §7，契約、估算與營運工作留在 [09 §4.1](../09-backlog.md#41-第七輪2026-10-25-r7-審查起留下的實作項目)（BL-61～65）。

## 1. 總評

- **穩的部分**：hash chain 與 Z3 副簽；跨 run 的錨點編號抓得到委任中段的回捲；裁決 → 叢集 → 發現項的 hash 鏈；B 階段 job 與稽核事件的雙向對帳；裁決完全由程式重算；strict JSON；文件、程式、測試三者的機械一致性。
- **不足分三類**：
  1. **錨定模型還有三個面沒蓋到**：未錨定的 `run_status_changed` 能重新打開已完成的 run；報告 manifest 沒有真的被 `report_published` 綁住；關卡紀錄的內容沒有釘進 `gate_decision`，核准者用自己的金鑰就能改寫已決定的紀錄。
  2. **裁決的兩個單點**：θ_reject 沒有「高於任何單張反駁票」的守衛；`trials.sampling: sampled` 是自填的開關。另有四個較小的邏輯缺口（同根平均讓 S 下降、分析者不同意被事先登記蓋過、作者不明當成獨立、校準汙染欄位沒有效果）。
  3. **文件被九輪修補堆成分層**：每份文件開頭 40～100 行的版本摘要、約 840 個 `v0.x` 標籤、README 狀態列停在第八輪；幾個契約缺口（harness 的可觀測性、審查者資格、人力估算）。

## 7. 排名調整與改變做法

- **「`run_log_state` 只採計已錨定的狀態變更」沒有做**：進行中的 run 的最新狀態變更本來就可能在未錨定的尾端，這樣做會誤報；改以「`run_end` 之後不能再有任何行」達到同樣效果。第九輪在突變驗證時拿掉了「有 `run_end` 錨點的 run 一定是終態」這條檢查（它被狀態規則遮蔽），這一輪的重新打開正是從那裡繞過的；現在的規則與 run 紀錄無關，不會再被遮蔽。
- **manifest 的 `audit_log` 產物沒有改成「沒有事件就推導為 null」**：那會連帶產生 `E-SCHEMA`；新的反向檢查已經對沒有事件的 manifest 報錯。
- **兩個改變裁決語意的項目依建議採用**（使用者授權自行決定）：根內取最強一票、棄權以擲硬幣計分。
- **錯誤碼表的整併延到 BL-64**：要把同一錯誤碼散在多個版本列的說明合併重寫；PR3 已經約 1,200 行，只拿掉表中的標籤。
- **自動拿掉標籤時誤刪兩段內容**（03 的 rule_version 歷程、08 的 `edge_ip_ranges` 來源），已手動恢復並由測試守住。
- **突變驗證發現兩個舊測試被遮蔽**：第八輪 `derived_from` 的測試（在第九輪就已被血統一致性檢查遮蔽）與第九輪 θ 保留切分的測試（被這一輪的保留切分大小檢查遮蔽）；兩者的斷言改指它們守的那一則訊息。
