# 設計審查紀錄：第七輪（2026-10-25 r7）

> **這份紀錄的用途**：保存第七輪審查的發現與處理方式，讓 v0.5 → `rule_version 05-v0.6` 的每一項修正都能追溯到審查發現；也列出沒有採納、改變做法或留給待辦清單的項目。
>
> - **審查對象**：main 的 `cec8fb8`（BL-14、16～20、40 合併之後）。
> - **方式**：三個彼此獨立的唯讀審查，分別看方法論與架構、validator 與 schema 能否被繞過、裁決／統計／校準；另有一份使用者提供的外部審查（5 項）。每一項繞過都先在記憶體中重現（一致地重算、重簽後 `run_all` 仍是 `[]`），再排入修正。
> - **處理原則**：依 [CONTRIBUTING.md](../../CONTRIBUTING.md)，每個宣稱「修好」的錯誤都有回歸測試：測試在修正前的 commit 上失敗、修正後通過，並且逐一停用每個新檢查，確認對應的測試會失敗（突變驗證）。驗證結果寫在各 PR 的說明中。
> - **結果**：第 1～5 組全部處理，分 6 個 PR 合併；沒有採納 1 項，3 項改變做法，6 項執行期工作留在 [09 §4.1](../09-backlog.md)。

## 1. 總評

- **做得好的地方**：裁決完全由程式碼決定，規則輸入都由 validator 重算；R0～R13 的決定表全部可達；校準前一律採安全預設；對照組讓 INVALID 永遠不算 PASS；Scope Proxy 是真正的強制點；統計界限計算正確，前導實驗事先登記。
- **主要不足**：
  1. validator 仍有能偽造或跳過人工關卡的路徑，最嚴重的是沒有簽章的 EXPIRED 紀錄可以核准或駁回（致命）。
  2. 沒有「流程完整性」檢查：叢集或發現項可以默默消失，範例本身就違反（K-014 既不是種子也不是 report-only）。
  3. 幾個設計前提不成立：W4 的「事先登記」沒有人審、支持權重偏向附和者、共享平台的所有權只靠聲明。
