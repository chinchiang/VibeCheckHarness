## D1 投票確認機制的去留（發現 B1）

**問題**：投票分支（R5 的第 11 列、R4 的自動駁回、R8、R15、門檻 θ、權重）佔了裁決規則最多的複雜度，但依文件自己的語料規模，它在可預見的時間內多半開不起來。

**證據**
- **[已讀]** `05:412–423`：全語料 610 個正例；校準切分 ≥250 個。最大的桶（authz 90 個）在校準切分約 37 個正例。
- **[代理]** `05:554–565`：可行的確認門檻要 ≥40 個經投票分支確認的叢集、≥10 個應用。
- **[已讀]** `05:226`（R8）自承「在 `E-CAL-THETA` 成立時不會觸發」，是防禦縱深。
- **[推測]** 「多半開不起來」是由上面的數字推論的，沒有模擬驗證。

**選項**
- **A 維持現狀。** 代價：每次審查都繼續在這條不會執行的路徑上花時間；規格份量不減。
- **★B 保留規則與程式，但在 05 明確標為「校準證明可行後才啟用」，並加一張可行性表**（每桶在校準切分的預期叢集數對照門檻）。v1 的確認只靠可執行證明、強工具佐證與人。代價：小，純文件；不升版、不動範例。
- **C 把投票分支從規則與程式中移除。** 代價：大；`rule_version` 升版、所有裁決範例與數百個測試要改；將來校準可行時要加回來。

**建議 B 的理由**：問題是「複雜度佔用審查心力」，不是規則本身錯。標示清楚加上可行性表，成本最低，也誠實。C 的代價與收益不成比例。

## D2 自動駁回不經人審（發現 B3）

**問題**：兩條路徑會把叢集直接判為 `REJECTED`，不成為種子威脅、不進人工關卡：
- R0：成員的證據沒有任何一項接地，且至少一項找不到。
- R4：單一家族回報、沒有工具訊號、反駁分數 S ≤ −θ_reject。

受測 repo 是攻擊者可控的輸入，所有驗證者讀同一份程式碼。一段偽裝的 guard 或註解可以同時誘導所有家族反駁。R0 也可能把真缺陷靜默駁回，因為 LLM 常改寫片段而不是逐字引用。

**證據**
- **[已讀]** `05:217`（R0）、`05:221`（R4）。
- **[已讀]** `06:28`：lite 不做抽查。
- **[已讀]** 範例的 `theta_reject` 目前是 null（不可行），所以 R4 的自動駁回現在不會發生；R0 則隨時可能發生。
- **[代理]** 校準語料只有良性誘餌，沒有含注入內容的對抗樣本。

**選項**
- **A 維持現狀。** 代價：一旦 θ_reject 校準成可行，就多一條可被操弄的自動漏報通道。
- **★B rubric 嚴重度為 critical／high 的叢集，R0 與 R4 不直接駁回，改為 `DISPUTED` 送 G2。** 其餘維持。代價：中；升 `rule_version`；G2 佇列在高嚴重度時變長（但 G2 本來就只收這類）。
- **C 全面取消自動駁回：R0 與 R4 的結果改成新的註記「低優先、未驗證」，列入報告與抽查。** 代價：較大；新增一種狀態或註記要貫穿 schema、報告、種子威脅規則。

**建議 B 的理由**：嚴重度由程式依 inventory 計算，不是 LLM 自報，拿它當分流條件不會被注入繞過。B 把風險最高的那一段交給人，改動範圍可控。

**不論選哪個，建議另外做**：校準語料加入對抗子集（植入缺陷＋誘導反駁的註解），θ_reject 的可行條件加上「對抗子集的真缺陷駁回數為 0」。這屬於 D9。

## D3 「G2 接受」當作事先登記的入口（發現 B4）

**問題**：LLM 撰寫的 W4 測試，只要叢集在 G2 被接受，之後的 FAIL 就算「事先登記」，可以升到最高等級 `CONFIRMED_EXECUTABLE`。但 G2 在 W3、早於 W4：人按接受時測試還不存在，他看的是叢集，不是 oracle。

第十四輪審查想修的正是「沒有人讀過 oracle 就能確認」，這個入口等於把同一個漏洞留了一條路。

**證據**
- **[已讀]** `derive.py` 的 `g2_accepted` 與 `preregistered`：W4 且非程式產生的 oracle，條件是「G2 接受且對照 PASS」。
- **[已讀]** `05:193`：「叢集經 G2 逐項 accept（人看過這一項）之後…才把它算事先登記」。
- **[代理]** `02:384–389`：G2 佇列只收 `DISPUTED`、高嚴重度的 `UNCORROBORATED` 與 `no_eligible_verifier`。所以一般 `LIKELY` 叢集永遠拿不到這個資格，爭議較大的反而拿得到。

**選項**
- **A 維持現狀。** 代價：最高等級的裁決可能建立在沒有人讀過的 oracle 上。
- **★B 移除 G2 這個入口；改為 W4 之後加一個輕量的人工步驟，逐項核准「LLM 撰寫且 FAIL 的 W4 測試」的 oracle，並以測試案例的 hash 綁定。** 核准後才算事先登記。代價：大；升 `rule_version`；關卡流程、gate-record schema、範例與變體都要改；多一個人工步驟。
- **C 移除 G2 入口，不加新步驟：LLM 撰寫的 W4 測試最高只到 `LIKELY`。** 代價：中；升版、改範例；校準前能到 `CONFIRMED_EXECUTABLE` 的路徑只剩程式產生 oracle 的測試與 G4 核准的黑箱測試。

**建議 B 的理由**：C 最簡單，但白箱階段的確認能力會明顯變弱。B 多一個步驟，卻讓「事先登記」名副其實。若您想先求簡單，C 是合理的過渡，之後再升級成 B。

## D4 結果分析 LLM 可否決確定性證明（發現 B5）

**問題**：只要結果記有合格的分析者且它不同意解讀，不論解讀是否已事先登記，結果都降為「不確定」。分析者讀的是受測應用的回應或測試輸出，屬於攻擊者可控的內容，可被誘導輸出「不同意」，把一個 G4 核准、重播成立的確定性 FAIL 降級。

文件自己也說過，事先登記時這一步「沒有增加資訊，只會讓證明依賴 LLM」。

**證據**
- **[已讀]** `derive.py` 的 `classify_result`：`if disagreement: return "E_inc"`，註解寫明「pre-registered or not」。這是第十輪審查刻意改的（先前是事先登記優先）。
- **[已讀]** `05:197`。

**選項**
- **A 維持現狀**（第十輪的決定）。代價：單一 LLM 握有降級否決權。
- **★B 事先登記的結果不因分析者不同意而降級；改為加註 `analyst_disagrees` 並列入人工複核清單。** 未事先登記的結果維持現狀。代價：小；升 `rule_version`；可能動到一兩個範例。
- **C 事先登記的結果完全不呼叫分析者。** 代價：小；但失去「分析者指出解讀有問題」這個訊號。

**建議 B 的理由**：保留訊號、移除否決權。注意這會推翻第十輪的決定，請確認當時改成現狀的理由（審查紀錄 `review-2026-10-27-r10.md`）不再適用。我沒有讀那份紀錄。

## D5 安全等級對未宣告的副作用 fail-open（發現 C1）

**問題**：安全等級信任 HTTP 語意與人工宣告。GET 預設算唯讀（S0），只有列在種子清單 `state_changing_reads` 的才升級。但 AI 生成的應用正是最不遵守 HTTP 語意的對象：`GET /api/x/delete?id=`、`GET /logout`、有副作用的 GraphQL query，都會以 S0 在沒有人工關卡的情況下執行。

**證據**
- **[已讀]** `04:547–553`、`04:749`、`safety.py` 的 `is_mutation`：GET 只有在 `state_changing_reads` 中才算寫入。
- **[代理]** `04:774`：LLM agent 測試一律 base S1，副作用只看宣告。
- **[實測]** 本次已把 `is_mutation` 對未知方法改為 fail-closed（PR #57），但 GET 的預設沒有動。

**選項**
- **A 維持現狀。** 代價：副作用的防線取決於基礎設施擁有者宣告得完不完整。
- **★B 預設反轉：W0 盤點無法證明 handler 唯讀的 GET，一律當寫入（≥ S1、要綁種子）。** 已知唯讀的端點列入 `read_only_endpoints`。代價：中；不升 `rule_version`（這是安全等級規則）；黑箱範例的安全等級可能改變，要重簽；seed manifest 要多宣告一些端點。
- **C 只在 06 §3 明列這項限制，不改規則。** 代價：小；風險不變，只是誠實。

**建議 B 的理由**：這與本次 `is_mutation` 的 fail-closed 修正是同一個原則。代價是測試設計者要多宣告唯讀端點，但這比漏掉一個有副作用的 GET 便宜。

**我不確定的地方**：W0 的抽取器「能不能判定 handler 唯讀」取決於尚未實作的程式。B 的實際效果要等抽取器存在才知道；在那之前等於「所有 GET 都要宣告」。

## D6 沒有正對照的 PASS 仍輸出統計上界（發現 C2）

**問題**：測試案例只強制「可達性」對照。沒有「oracle 能失敗」對照的 PASS 仍算合格 PASS，報告還附「違反率上界 4.9%」。但 LLM 類測試的 oracle 資料常來自受測應用自寫的 log；有漏洞的程式路徑若沒寫 log，就會得到假 PASS。此時上界量的是「log 有沒有寫」，讀者卻會讀成安全保證。

**先前說法的修正**：裁決規則已經部分處理了這件事。**[已讀]** `05:227`（R11）：沒有正對照的 PASS 不會把已確認的叢集降級，只加註 `test_not_reproduced`。所以問題不在裁決，而在**報告仍輸出統計上界**，以及這類 PASS 與有正對照的 PASS 用同一個等級名稱。

**證據**
- **[已讀]** `checks.py:2501`：`E-TC-CONTROLS` 只要求至少一個 `reachability`。
- **[已讀]** `04:966`、`04:997`：範例 B 自承「會得到假 PASS」，`positive_control` 為 null。

**選項**
- **A 維持現狀。**
- **★B 沒有正對照的 PASS 另立等級（例如 `E_pass_weak`），報告不輸出統計上界，改寫「未觀察到違反；oracle 未經正對照驗證」。** 代價：中；升 `rule_version`；範例 B 的結果與報告要改、重簽。
- **C 強制正對照：oracle 資料來自受測應用，或威脅為高風險時，沒有 `oracle_can_fail` 對照就是驗證錯誤。** 代價：較大；範例 B 要補一個植入版對照；測試設計成本上升。

**建議 B 的理由**：B 修的是「報告誤導」這個核心問題，不強迫每個測試都準備植入版。C 更嚴謹，可以作為高風險威脅的後續要求。

## D7 lite 模式下自我核准的最高等級裁決（發現 B6）

**問題**：lite 模式只有一個人。設計在 G2 不准他駁回，理由是「不讀程式碼的使用者不該做最終決定」；卻在 G4 把他的核准當成 oracle 正確性的唯一保證，讓結果可以到 `CONFIRMED_EXECUTABLE`。G1 的存取矩陣也是模型提議、同一個人確認。報告首頁只標「未經職責分離」，沒有講到「結果正確性取決於自我核准」這一層。

**證據**：**[代理]** `02:169–170`、`02:616`、`02:649`。我沒有親自讀這幾行。

**選項**
- **A 維持現狀。**
- **★B 規則不變；lite 報告把這類確認改標為「自我核准的可執行證明」，並在首頁說明其意義。** 代價：小；報告清單的 schema 與範例加一個標示。
- **C lite 下 LLM 產生腳本的 FAIL 不算事先登記，最高 `LIKELY`；只有程式產生 oracle 的測試才給最高等級。** 代價：中；升版；lite 的黑箱階段幾乎拿不到確認。

**建議 B 的理由**：lite 的定位就是自查。誠實標示比限制等級更符合定位。這一項應與 lite profile（D10、BL-70）一起定案。

## D8 三家都獨立回報反而等級較低（發現 B7）

**問題**：分數 S 只加驗證票。三個家族時，「一家回報、另兩家支持」可以到 `CONFIRMED_CORROBORATED`；「兩家獨立回報、第三家支持」只有一張票，最高 `LIKELY`；三家都回報則沒有票。獨立發現的證據力通常不低於被動同意，等級卻相反。

**證據**：**[已讀]** `05:222–223`（R5 只看 S、R6 看獨立來源數）；**[代理]** `05:316`。

**選項**
- **A 維持現狀。**
- **B 把第一輪的獨立回報也折算進分數**（以回報者的 precision 校準）。代價：大；改計分、校準設計與所有範例。
- **★C 暫緩，併入 D1。** 這個問題只在投票分支啟用時才有實際影響；D1 若選 B（投票分支標為未啟用），這項也跟著暫緩，在可行性表旁註明。

**建議 C 的理由**：在投票分支本身開不起來的前提下，先修它的內部不對稱沒有收益。

## D9 校準主要假設比錯東西（發現 B2、B3 的語料部分）

**問題**：預先登記的主要假設比的是「同一模型取樣 3 次中 ≥2 次回報」對「3 個家族中 ≥2 個回報」。但管線實際上不用「≥2 同意」這條接受規則：單一家族回報的叢集不會被丟掉，它進加派、W4 與種子威脅。而這個檢定的結果會直接切換預設策略。另外缺一組關鍵對照：單一最佳模型取樣 3 次，加上同樣的工具與測試後段。

**證據**：**[代理]** `05:443–449`、`05:497–499`、`05:541–548`。我沒有親自讀 §5.6。

**選項**
- **A 維持現狀。**
