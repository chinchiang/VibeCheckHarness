# 設計審查紀錄：第九輪（2026-10-27 r9）

> **這份紀錄的用途**：保存第九輪審查的發現與處理方式，讓 `rule_version 05-v0.7` → `05-v0.8` 與錨定模型的每一項修正都能追溯到審查發現；也列出改變做法與留到之後的項目。
>
> - **審查對象**：main 的 `87a5175`（第八輪 PR #20～#23 合併之後）。
> - **方式**：三個彼此獨立的唯讀審查，分別看 validator 與 schema 能否在**沒有金鑰**的情況下被繞過、裁決／統計／校準邏輯、方法論與文件；另有一份使用者提供的外部審查（2 項，都重現）。每項繞過都附在記憶體中重現的 probe；最嚴重的幾項由主審查者自己重跑。
> - **處理原則**：依 [CONTRIBUTING.md](../../CONTRIBUTING.md)，每個宣稱「修好」的錯誤都有回歸測試：測試在修正前的 commit 上失敗、修正後通過，並且逐一停用每個新檢查確認對應的測試失敗（`tests/mutations/r9_*.json`，以 `tools/mutation_check.py` 重跑）。
> - **結果**：四個 PR 全部合併；3 項改變做法（§7），4 項契約與 1 項範例工作留在 [09 §4](../09-backlog.md)（BL-58～60，加上第八輪留下的項目）。

## 1. 總評

- **做得好的地方**：決定表 13 列與 `adjudicate()` 在 860,160 組輸入上零不符；K-014 的權重數字可由校準計數重現；簽署文件與 `config_pins` 繞不過；終態 run 裡事後改裁決會被 `verdict_sha256`、`report_manifest_sha256` 與 E-PIPELINE 三重釘選抓到；第八輪修的 B4／W4 執行證據與 G2 `item_sha256` 擋住了本輪的嘗試。機械性檢查在審查當下全部通過（validator 4,328 項、1,148 個測試、0 個壞連結、錯誤碼表與程式雙向一致）。
- **根本不足**：validator 把**未簽署的 Z1 文件**（run 紀錄、叢集、發現項、種子威脅、報告 manifest）與**未錨定的稽核行**當成事實，而 06 §1.8 以為 `artifact_stored` 與 run 紀錄裡的錨點清單已經蓋住它們。最嚴重的一項：錨點清單是從稽核檔推回 run 紀錄的，所以只控制 Z1 的人可以把已完成的 run 截回較早的錨點，刪掉 B4 證據、G5、B5 裁決與報告，validator 零錯誤。
- **第二類**：裁決的獨立性在「票」這一層仍有漏洞——同一血統根的兩張票相加、W4 測試由回報家族自己寫自己審、θ 的可行性是自填的布林值、只答容易題目的模型保住高權重、同一血統的矛盾 `derived_from` 宣告依檔案順序決定根。
- **第三類**：設計契約的矛盾與缺口——所有權驗證的方法沒有綁回 ROE、ROE 到期的結果仍有三個版本、ASI09 抽查的母體在 validator 裡記錄不了、跟進 run 沒有自己的 G1、人力與周轉時間沒有量化。

## 7. 排名調整與改變做法

- **計畫的「G4 已核准但沒有 job 的非終態 run 發警告」沒有做**：那是合法的中間狀態；回捲改由錨點編號抓，比警告更準。
- **W 階段的切片、Commander 計畫、DFD、inventory 內容仍沒有錨定**：發現項與叢集改由裁決的 hash 鏈蓋住、種子威脅由 `artifact_stored` 蓋住；其餘的缺口寫在 06 §1.8。
- **W4 作者獨立性用既有的角色規則**（agents.yaml 的 test_generator／test_critic），沒有在 w4-testcase 加逐測試的作者欄位：與第八輪 `E_fail_u` 的獨立性同一條規則，逐測試的作者要等執行器才有可信的來源。
- **Lite 的抽查**選擇「不做並標示」，沒有做「自行抽查」的例外：一個人重看自己的決定不提供獨立性。
- **第二個小型 bundle 沒有建**：完整的第二個簽署 bundle（金鑰、ROE、委任、run）工作量與風險都大，而它要證明的路徑都已有記憶體中的測試；改以路徑表把「哪條路徑由哪個測試作證」寫明並由測試守住，bundle 列為 BL-60。
- **兩個檢查在突變驗證時拿掉**：「有 `run_end` 錨點的 run 一定是終態」被「狀態等於最後一筆狀態變更」蓋住；「裁決的收件時間只取已錨定事件」被「未錨定的 `verdict_changed` 不是裁決」蓋住。兩者互相遮蔽，留著只會讓突變驗證抓不到。
