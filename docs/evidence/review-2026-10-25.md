# 設計審查紀錄（2026-10-25）

> **這份紀錄的用途**：保存 2026-10-25 對 v0.4 設計與 v0.5 分支的審查結論，讓第六輪（v0.5）的每一項修正都能追溯到審查發現；也列出尚未處理的項目與處理順序。
>
> - **審查對象**：main 上的 v0.4（commit `1e9e61f`），以及 v0.5 分支 `codex/design-v0.5-safety-boundaries`（commit `07658d7`）。
> - **方式**：五個唯讀審查代理分頭做對抗式審查（裁決與校準、工具包自身的信任錨與稽核、方法論與威脅對照、可實作性與跨文件一致性、validator 繞過與測試弱點），每項發現附 `檔案:行號`；「已用實驗確認」者是在記憶體中改動範例 bundle 後實際執行 validator 的結果，沒有改動 repo。v0.5 分支由主審查者逐行讀 diff 並試合併。
> - **行號**：v0.4（`1e9e61f`）的 `檔案:行號`。
> - **處理原則**（依使用者決定）：R10 保留 v0.4 的語意（`E_proof` 覆蓋 G2 駁回），v0.5 分支的報告要求併入 B6；從第 0 組開始處理。
> - **第 0 組已處理**（v0.5，見 §7）；第 1–5 組尚未處理。

## 1. 總評

- **設計整體仍合理**：資料模型（schema）與驗證器（validator）的「推導、不宣告」原則、金鑰登錄（key registry）單一信任根、Audit Writer 收件時間為準、Z3 副簽錨點、fail-closed 的種子綁定與安全等級計算，在這一輪的對抗式測試中大多撐住；五個代理都點名這些是做得好的部分。
- **但 v0.4 五輪修得太快，留下一批「規則只檢查一半」的洞**：最嚴重的三個是（1）非終態 run 沒有稽核檔時，所有「收件時間」規則悄悄退回自填時間；（2）`testresult.cluster_ids` 只檢查是超集合，測試結果可以掛到任何叢集改寫裁決；（3）R10 沒有分階段，含 G2 駁回的誠實 bundle 反而驗不過。這三項都用實驗確認。
- **v0.5 分支的最大問題不是內容，是基底**：它從 v0.3 分出來，沒有 v0.4 的任何修正，直接合併會把五輪修正還原大半（13 個檔案衝突）。內容本身有四項值得保留的補充（還原範圍排他、CAS 委任隔離、取樣獨立性、G1／G3 沿用停用）。

### 4.2 中優先

**信任錨與稽核**
- T-2 `opened_at` 只在核准者簽的紀錄裡，從不與 `gate_opened` 事件或 `run.gate_records` 比對；偽造它可以躲過 `E-GATE-TIMEOUT`、抵銷 `E-GATE-EXPIRED-EARLY`、操控 G5 的 `window_end`。
- T-3 「EXPIRED 是唯一沒有簽章的結果」（08:341、schemas/README:117）做不到：`E-SIG-MISSING` 對每個未簽的核准者都會報；既有測試靠重簽 EXPIRED 紀錄才通過。
- T-4 `z3-executor` 服務金鑰在 `persons` 中，可以簽 `initiator_claim`（不要求角色）、當 run 或關卡的發起者，繞過「必須由人認領」。
- T-5 委任設定／ROE 的金鑰效期與撤銷是以自填 `issued_at` 判斷，不是 03 §6.1 說的 G0a／G0b 收件時間；`check_backdating` 不看 `not_after`，過期（非撤銷）的金鑰仍可倒填新 ROE。
- T-6 `verification.key_registry_version == registry.version` 是嚴格相等 → 任何一次撤銷（版本號加一）讓所有歷史 G0a／G0b 紀錄失效。
- T-7 `legal_review.attested_by` 的預期指紋是「目前未撤銷的金鑰」→ 法務審查者例行輪替金鑰就讓 ROE 驗不過（`E-SIG-EXTRA`＋`E-SIG-MISSING`），與 §6.1 步驟 5 矛盾。
- T-8 03 §5.8／08 §6.3 說重複的稽核事件會寫入、讀取時去重；validator 卻把重複當錯誤（`E-AUDIT-IDEMPOTENCY`）→ resume／重試過的 run 驗不過。
- T-9 Z3 副簽只蓋 `{run_id, seq, prev_hash}`：最後一個錨點自己的 `ts`／payload 可以改而不報錯；Z3 看不到鏈的內容，所以 Z1 在 run 進行中就能讓偽造的鏈被簽；z3 金鑰三種用途沒有 domain separation。
- T-10／V-6／A-6 `calibration.yaml`、`crosswalk.yaml` 影響裁決卻不在 `config_pins` 也不簽章；`verdict_inputs` 用自填的 `score`／`theta`（容差 5e-4）→ UNCORROBORATED 可翻成 LIKELY。
- T-11 `ip_problem("::c0a8:101")`（IPv4-compatible）放行；`normalize_for_match` 沒有承諾的「雙重編碼拒絕」，`%00` 段可以躲過排除清單。
- V-7 未錨定尾端只是警告：在尾端偽造 `tool_invocation_end`（不需 Z3 金鑰）就能當弱 SARIF 訊號把叢集推到 LIKELY。

**裁決與校準**
- A-3 ABSTAIN 票若權重＞0 會算 `weighted_valid` 並計入 `diversity_degraded` 的家族 → 一張棄權票可以解除 R8 上限，讓單一支持家族得到 CONFIRMED_CORROBORATED（在 K-014 上驗證）。
- A-4 引用相關性只比檔名：`routes/invoices.ts:99999`、甚至沒有行號都算有效；05:208 承諾的「引用通過接地比對」沒有任何地方檢查。
- A-5 相關性規則對反駁票不利：反駁證據通常在別的檔案或 inventory 事實 → 被當棄權 → 叢集更容易 LIKELY／CONFIRMED。
- A-6 `invalidated_by`／`valid_for_model_keys` 從不影響 `Index.weight`；模型版本漂移不與 `calibration.config.models[].version` 比對；§5.8「重跑前 w＝0」沒有強制。

**方法論與威脅對照**
- M-1 DB 目標的所有權證明自相矛盾：06 #18 說沒有技術性證明，02:578/583 卻會移除 DNS TXT 失敗的目標，roe.schema 要求 `token_ref`；`platform_rules` 對 `supabase.co` 的 DB 主機跳過 → Supabase 託管的 staging（MVP-0 的目標）用不了 `db_access`，種子、STATE_DIFF、寫入範圍全部 S3。
- M-2 範例 A 的 oracle `status ∈ {403,404}` 把 405／422／500 都當 FAIL → 事先登記 → `E_proof` → 假的 CONFIRMED_EXECUTABLE；CTL-02 正對照只覆蓋 body 子 oracle。
- M-3 機率型重播（n_r＝20、`k_r ≥ fail_k_min`）會把約 36% 的真實 5% 違反率降成 `E_inc`，與「一次呼叫即違反」矛盾；validator 從不檢查 `replays == replay_n`（n_r＝1 也過）。
- M-4 G3 超出上限「視同駁回」（02:538）沒有 GateRecord 表示法；D5 與 R13 需要 G3 的 reject 決定，而 over-cap 的定義是「沒有決定」→ `B3_validate_artifacts` 會擋住 G4，或簽署者替自動決定背書。
