# 設計審查紀錄：第八輪（2026-10-26 r8）

> **這份紀錄的用途**：保存第八輪審查的發現與處理方式，讓 `rule_version 05-v0.6` → `05-v0.7` 的每一項修正都能追溯到審查發現；也列出改變做法與留到之後的項目。
>
> - **審查對象**：main 的 `e5fa57d`（第七輪 PR #14～#19 合併之後）。
> - **方式**：三個彼此獨立的唯讀審查，分別看 validator 與 schema 能否被繞過、裁決／統計／校準邏輯、方法論與文件；另有一份使用者提供的外部審查（6 項，全部重現）。每項繞過都附在記憶體中重現的 probe；最嚴重的幾項由主審查者自己重跑。
> - **處理原則**：依 [CONTRIBUTING.md](../../CONTRIBUTING.md)，每個宣稱「修好」的錯誤都有回歸測試：測試在修正前的 commit 上失敗、修正後通過，並且逐一停用每個新檢查確認對應的測試失敗（突變清單從本輪起留在 `tests/mutations/`，以 `tools/mutation_check.py` 重跑）。
> - **結果**：第 1～5 組全部處理，分 4 個 PR 合併；2 項改變做法（排名與做法見 §8），5 項營運與執行期工作留在 [09 §4.1](../09-backlog.md)（BL-53～57）。

## 1. 總評

- **做得好的地方**：裁決完全由程式碼決定，validator 自己重算每個輸入；錯誤碼表與程式雙向一致（296 個）；關卡時間以 Audit Writer 的收件時間為準；回歸測試紀律、雙 OS／雙 Python 的 CI；06 §3 的限制清單誠實。機械性檢查在審查當下全部通過（validator 4,049 項、1,056 個測試、0 個壞連結）。
- **主要不足**：
  1. **不需要金鑰的 validator 繞過**：沒執行過的 job（PENDING／EXECUTING／INTERRUPTED／STOPPED）可以掛上測試結果並把叢集確認為 CONFIRMED_EXECUTABLE；同一個 job 的第二份結果不比對 pin；高嚴重度叢集可以因 W4 重新裁決而跳過 G2。
  2. **關卡的結構性規則沒有檢查**：G0b 可以不存在或 `VERIFY_FAILED`、`initiator_claim` 可以拿掉、關卡順序只看自填的 `opened_at`。這些需要 Z3 金鑰才能偽造（03 §13 已承認「同時握有 Z1 與 Z3 金鑰者可整條重寫」），所以列高、不列致命；但流程出錯時 validator 也抓不到。
  3. **校準與獨立性的邏輯缺口**：平滑後 a 可以等於 1，讓最準的驗證者權重歸零；獨立性仍數 family、不數血統的根；θ 沒有符號與範圍檢查；`derived_from` 循環會依起點回傳不同的根。
  4. **run 生命週期與完整性模型不一致**：ROE 失效有三種結果；`regression` run 規格有但 validator 禁止；跟進 run 範例走了文件說不存在的路；裁決內容、報告、SARIF、`toolkit.yaml` 都在錨定鏈之外。

## 8. 排名調整與改變做法

- **F1／F3／F4 的排名**：審查代理列為致命；因為需要 Z3 金鑰、屬 03 §13 第 16 條已承認的限制，改列高。F2a、F2b、F5 不需要金鑰，是本輪最嚴重的。
- **嚴重度 rubric 的未知輸入**：資料等級無法對應或位置沒有端點時不加減分（只有可達性未知視同 internet），否則範例中每個叢集都是 critical，rubric 失去區分力；寫進 08 §11.17 第 6 點。
- **classify_result 的執行事件條件**：只要求「恰一筆已錨定、outcome 相符的 `sandbox_job_end`」，pin 的比對留給 `E-JOB-AUDIT`（bundle 有錯誤就不成立），避免測試中每次改結果都要重鏈。
- **regression run 的檔案範例**：沒有另建一個完整的 run（稽核紀錄、關卡、叢集）；在記憶體中以跟進 run 改 kind 驗證。之後若需要，連同 BL-48 的 run kind 一起做。
- **CHANGELOG 的版本**：設計文件版本不升（規則寫在 CHANGELOG 開頭），程式與 schema 註解以「v0.7」標示本輪變更；`toolkit_version` 與 `pyproject` 對齊 0.5.0。
